# Почему std::any не нужен в этом проекте

## 1. Стоимость доступа

`std::any` использует **type erasure**: значение хранится через
указатель на базовый класс, а конкретный тип «стёрт». Это означает:

**Heap-аллокация** для каждого значения, превышающего размер SBO
  (small buffer optimization, обычно ~2–3 слова). В нашем случае
  `TextBody`, `SystemNotice`, `Reaction` содержат `std::string`
  (32 байта на libstdc++), что почти наверняка превышает SBO.
**`any_cast<T>`** проверяет тип в **runtime** через `typeid`
  и бросает `std::bad_any_cast` при несовпадении. Это ветвление
  и потенциальное исключение на каждом доступе.

`std::variant` хранит данные **inline** (размер = max(альтернативы) +
дискриминатор). Никаких heap-аллокаций для самого variant.
`std::visit` разрешается через таблицу переходов или switch —
без исключений и без `typeid`.

## 2. Проверка на этапе компиляции

`std::variant<TextBody, SystemNotice, Reaction>` фиксирует набор
типов в сигнатуре. Компилятор:

**Проверяет полноту `std::visit`**: если вы забыли обработать
  `Reaction`, код не скомпилируется (при использовании overloaded
  без оператора по умолчанию).
**Не позволяет положить произвольный тип**: `variant = 42` —
  ошибка компиляции. С `std::any` это прошло бы молча и сломалось
  только в runtime.

В нашем проекте набор типов команд и тел сообщений **замкнут и
известен заранее**. `std::any` дал бы иллюзию гибкости, но на
деле мы получили бы:
-лишние аллокации,
-runtime-ошибки вместо compile-time,
-невозможность гарантировать, что все случаи обработаны.

**Вывод**: `std::any` полезен, когда набор типов открыт и неизвестен
на этапе компиляции (например, плагинная архитектура). Для замкнутого
набора типов `std::variant` строго лучше по производительности и
безопасности.
