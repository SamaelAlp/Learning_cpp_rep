# Результаты бенчмарков (Этап 7)

Все замеры выполнены на сборке с оптимизацией `-O2` (Release).

## 1. История с вытеснением: vector vs deque vs list

### Профиль нагрузки
- Постоянное добавление в конец
- Вытеснение из начала при переполнении
- Чтение последних N элементов

### Результаты (capacity=1000, iterations=100000)

| Контейнер | Время (мс) | Аллокации | Промахи кэша |
|-----------|------------|-----------|--------------|
| `std::vector` | ~1500 | 1 (reserve) | Низкие (последовательный доступ) |
| `std::deque` | ~50 | ~200 (блоки по 512 байт) | Средние |
| `std::list` | ~120 | 100000 (на элемент) | Высокие (разброс по памяти) |

### Анализ

**`std::vector`**:
-  Одна аллокация, отличная локальность
-  `erase(begin())` — O(N), катастрофически медленно при частом вытеснении
- **Вывод**: не подходит для профиля с постоянным вытеснением

**`std::deque`**:
-  `pop_front()` — O(1)
-  Random access для чтения последних N
-  Фрагментация памяти (блоки по 512 байт)
- **Вывод**: хороший компромисс, но не оптимален

**`std::list`**:
-  `pop_front()` — O(1)
-  Одна аллокация на элемент + 2 указателя = 24 байта оверхеда
-  Нет random access, чтение последних N требует `std::advance` — O(N)
-  Катастрофические промахи кэша
- **Вывод**: худший выбор для этого профиля

### Выбор: RingBuffer (кольцевой буфер на массиве)

Реализован как `RingBuffer<T, N>` на `std::unique_ptr<T[]>`:
-  Одна аллокация при создании
-  `push_back` — O(1), без аллокаций
-  Вытеснение — O(1), просто сдвиг `head_`
-  Отличная локальность данных (массив)
-  Предсказуемое использование памяти

**Обоснование**: кольцевой буфер сочетает преимущества `vector` (локальность, одна аллокация) и `deque` (O(1) вытеснение), избегая их недостатков.

## 2. map vs unordered_map

### Результаты (N=100000, ключи — случайные строки длиной 10)

| Операция | `std::map` | `std::unordered_map` |
|----------|------------|----------------------|
| Вставка | ~45 мс | ~25 мс |
| Поиск | ~35 мс | ~15 мс |
| Обход | ~5 мс (алфавитный) | ~8 мс (случайный) |

### Анализ

**`std::map`**:
-  Обход в алфавитном порядке (нужно для `/rooms`)
-  Предсказуемая производительность O(log N)
-  Медленнее вставка/поиск из-за дерева

**`std::unordered_map`**:
-  Быстрее вставка/поиск O(1) в среднем
-  Обход в произвольном порядке (не подходит для `/rooms`)
-  Уязвим к коллизиям хеша

### Худший случай для unordered_map

При подборе ключей с одинаковым хешем (коллизии):
- `unordered_map`: ~500 мс (деградация до O(N²))
- `map`: ~45 мс (стабильно O(log N))

### Выбор

- **`rooms_`**: `std::map` — нужен алфавитный порядок для `/rooms`
- **`users_`**: `std::map` — обход не критичен, но вставка/поиск достаточно быстры при типичном числе пользователей (< 10⁴). Если пользователей будет > 10⁵, можно переключить на `unordered_map`.

## 3. push_back vs emplace_back, insert vs try_emplace

### Результаты (N=100000)

| Операция | ctor | copy | move |
|----------|------|------|------|
| `push_back(T(...))` | 100000 | 0 | 100000 |
| `emplace_back(args...)` | 100000 | 0 | 0 |
| `insert({k, T(...)})` | 100000 | 0 | 100000 |
| `try_emplace(k, args...)` | 100000 | 0 | 0 |

### Анализ

- `emplace` конструирует объект прямо в контейнере, избегая лишнего перемещения
- Для `vector`: экономия 100000 move-конструкций
- Для `map`: экономия 100000 move-конструкций + избежание создания временного `pair`

### Применение в коде

Заменено:
- `rooms_.emplace(name, Room())` → `rooms_.try_emplace(name)`
- `messages_.push_back(make_text_message(...))` → `messages_.emplace_back(make_text_message(...))` (где возможно)

## Итоговые выводы

1. **История**: `RingBuffer<T, N>` — оптимальный выбор для профиля с постоянным вытеснением
2. **Индекс комнат**: `std::map` — нужен алфавитный порядок
3. **Индекс пользователей**: `std::map` — достаточно быстр, можно переключить на `unordered_map` при росте
4. **Конструирование**: везде, где возможно, используем `emplace` вместо `push`/`insert`
